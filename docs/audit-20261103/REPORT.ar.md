## ما نُفذ فعلياً

- قراءة المستودع ومراجعة بوابات التطبيقات والهوية والكوزمتك والإشعارات، مع قراءة مقاطع محددة من Worker المشترك المنشور `salonati-api`. لم تُراجع جميع وحدات ذلك العامل بالكامل.
- قراءة حالة Cloudflare Pages: التطبيقات الأربعة ناجحة ومنشورة على الالتزام أعلاه؛ لا يعني ذلك اجتياز الأمن أو الاستقرار.
- قراءة مخطط جداول D1 الفعلي وعلاقاتها المعلنة وفحص المشغلات والعلاقات غير المعلنة الرئيسية، دون استخراج بيانات شخصية للتقرير.
- تنفيذ إصلاحات برمجية واختبارات SQLite محلية في الذاكرة، مع جلسات وحسابات ووسائط تجريبية مصطنعة.
- بناء التطبيقات الأربعة في وضع `--live` ومقارنة أصولها بمرجع الإنتاج: **277 ملفاً غير العامل متطابقة بايتاً ببايت**، وتحليل **60 سكربت وعاملاً مولداً** دون أخطاء صياغة.
- استخدام متصفح حقيقي لتحميل التطبيقات الأربعة وتبديل نموذج الدخول/التسجيل للزبونة والكوزمتك وتحديث الصفحات. جلسة إدارة موجودة في المتصفح أمكنها قراءة مجموعات الحجوزات؛ هذه ليست تجربة وصول مجهول ولا إثباتاً لتجاوز المصادقة.
- لم يُنفذ نشر أو دمج أو تغيير إعدادات أو أسرار أو حذف إنتاجي. جميع عمليات SQL المباشرة على الإنتاج كانت SELECT/PRAGMA للقراءة؛ أظهرت بيانات D1 الوصفية صفر صفوف مكتوبة.

## سلامة الحذف النهائي المرحلي

الملفان `deployment/account-deletion.staged.mjs` و`deployment/account-deletion.staged.sql` **غير مستوردين في أي مسار حي وغير منشورين**. الخدمة تسمح حالياً ببيئة `isolated-test` فقط. معامل المرجع سجل للمراجعة، وليس بديلاً عن التحقق من صلاحيات المشغل عند بناء واجهة إدارية مستقبلية.

الآلية المنفذة:

1. مطابقة مخطط الجداول الفعلي مع المخطط المراجع؛ ظهور جدول جديد أو تغير مخطط يمنع التنفيذ إلى حين المراجعة.
2. التأكد من الحساب ونوعه وهوية التطبيق الوحيدة؛ رفض الإدارة والهويات المشتركة/الملتبسة.
3. فحص الاعتماديات وسياسة الاحتفاظ. وجود حجز أو طلب أو اتفاقية مالية أو حركة مالية أو رابط مصدر قديم يمنع الحذف؛ لا اختلاق لسياسة احتفاظ ولا حذف للسجل المالي.
4. فحص الإشارات المشتركة للوسائط في JSON الخاص بالكوزمتك، وإعادة فحص الموانع ضمن المعاملة. المخطط الحالي يحتوي أيضاً على مفاتيح خارجية تمنع حذف وسيط مرتبط بحساب آخر.
5. في `D1.batch` واحدة: إنشاء مهمة تدقيق بقيمة تجزئة للحساب، تسجيل مفاتيح الملفات في صندوق أعمال، إزالة الجلسات/اشتراكات الزبونة، إزالة البيانات التابعة المسموح بها ثم الهوية والحساب. أي خطأ FK أو مانع في المعاملة يرجع جميع الخطوات.
6. بعد نجاح المعاملة فقط تُحذف الملفات الخارجية على دفعات. فشل R2 يبقي المهمة قابلة للاستكمال؛ الملف ذو المفتاح المشترك مع metadata باقية يُحتفظ به. روابط الوسائط الخارجية لا تُحذف.
7. إعادة الطلب ترجع المهمة نفسها، وإعادة استكمال الملفات لا تعيد حذف الملفات المكتملة. الحساب يُحذف أولاً مع جلساته فلا تبقى القدرة على الدخول أثناء انتظار تنظيف الملفات.

اختُبرت: إزالة حساب مالك بلا سجل تشغيلي، إزالة زبونة وجلساتها وإشعاراتها، بقاء حساب آخر، ملف مشترك، فشل R2 ثم الاستكمال، إعادة الطلب، منع مال ذي صلة، التراجع بسبب مرجع من حساب آخر، منع تغير المخطط، وعدم وجود مخالفات FK بعد الاختبار.

**القيود:** هذا ليس حلاً نهائياً للحسابات التي لها حجوزات/طلبات/أموال. يلزم اعتماد مدة الاحتفاظ وأساسها لكل سجل، وكيفية فصل البيانات الشخصية، وفحص قاعدة LEGACY_DB وأي مخازن أخرى، وتأمين استدعاء الخدمة، وربطها بعملية إدارة معتمدة، واختبار D1/R2 مرحلي فعلي. اختبار SQLite يحاكي واجهة D1 ولا يحل محل اختبار runtime الحقيقي. لا توجد ضمانة اتساق عالمية مع مخازن خارجية أو كود قديم يكتب بالتزامن؛ لذلك لم تُفتح هذه الخدمة للإنتاج.

## التنقل والاستقرار والمظهر

المثبت بالمتصفح: تحميل التطبيقات الأربعة؛ نموذج الدخول للزبونة والصالون والكوزمتك؛ تبديل التسجيل للزبونة والكوزمتك؛ بقاء صفحة الدخول صالحة بعد التحديث. الإدارة عرضت هيكلها مع اتفاقية الاستخدام، وكان هناك سياق إدارة قائم للقراءة. لم تُقبل اتفاقية ولم تُرسل بيانات تسجيل أو أوامر تعديل.

لم يُنجز: تدفق عمل داخلي شامل لكل دور، الهاتف الفعلي، محاكاة انقطاع الشبكة، الضغط، قياس مؤشرات الأداء، حفظ المدخلات أثناء العودة، كل الأزرار والنوافذ، تنفيذ حجز وطلب وإعلان كامل عبر المتصفح، تغيير كلمة المرور واستعادة الحساب، إرسال Push فعلي على جهاز. لا توجد ادعاءات نجاح لهذه الاختبارات.

لم يُعدّل CSS أو الألوان أو التخطيطات أو نصوص الواجهة أو أصولها أو أكواد خدماتها الأمامية. المقارنة البايتية تثبت ثبات الملفات الأمامية. تغير بيانات العرض المقصود هو حجب المحتوى غير المعتمد أو الحساب المعطل؛ لم تُنفذ مقارنة بصرية مصادق عليها لكل شاشة بعد الإصلاح لأن الفرع لم يُنشر ولم تتوفر جلسات اختبار داخلية لكل دور.

## ما يمنع إغلاق المهمة وما يحتاج اعتماداً

- مراجعة وإصلاح الحماية في Worker المشترك نفسه، وتحديد جميع مداخله العامة/روابطه القديمة؛ إصلاح Pages وحده لا يثبت عزل المنظومة كلها.
- إغلاق سباق التعطيل مع إنشاء الحجز في المصدر المشترك، وتدقيق جميع الكتابات القديمة التي قد تتجاوز البوابة.
- سياسة احتفاظ معتمدة للحجوزات والطلبات والمال والقانون والنسخ الاحتياطية، وحذف/فصل البيانات الشخصية المسموح به، وجرد كل مخازن الحسابات القديمة والملفات المشتركة.
- بيانات اختبار معزولة وجلسات مخصصة للأدوار الأربعة لاستكمال الاختبارات الداخلية والهاتف والشبكة والضغط والإشعارات الحقيقية.
- مراجعة قيود Google Maps من الحساب المالك، واستكمال مراجعة XSS ورفع الملفات والأسرار ومداخل SQL في API المشترك؛ الاستعلامات المعدلة تستخدم bind، وهذا لا يثبت سلامة كل المنظومة.
- مراجعة PR ثم اعتماد منفصل للدمج والنشر وأي migration أو تغيير إعدادات؛ نشر Worker الإشعارات منفصل عن Pages.
- أي حذف لحساب إنتاجي يحتاج اعتماداً صريحاً يحدد الحسابات والسياسة؛ لا ينطبق حذف الاختبار على الإنتاج.

النتيجة: توجد إصلاحات واختبارات قابلة للمراجعة، لكن لا شهادة جاهزية تجارية ولا موافقة على حذف إنتاجي ولا نشر تلقائي للإصلاحات من هذه المهمة.
