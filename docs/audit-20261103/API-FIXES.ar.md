# استكمال إصلاح API المشترك

التاريخ: 3 نوفمبر 2026. الفرع: `fix/security-deletion-audit-20261103`. الحالة: **إصلاحات المصدر مختبرة ومرفوعة للمراجعة، غير منشورة على الإنتاج**.

استُخرج المصدر الكامل للعامل المنشور `salonati-api` بقراءة API من Cloudflare. بصمة SHA-256 للنسخة الأصلية: `93ae7682954f929faac87e0ce9f4771b5f2efa2f389fe36f2b4df94a635fdfea`، وحجمها UTF-8 هو 703,542 بايت. أضيف المصدر في الالتزام المستقل `28d1d3b` قبل التزام الإصلاح لتسهيل مراجعة الفروق. الملف التنفيذي المستقل: `workers/salonati-api/worker.mjs`؛ بيانات المنشأ في `source-provenance.json`.

## الإصلاحات المنفذة في المصدر نفسه

| المشكلة | المعالجة | الدليل الاختباري |
|---|---|---|
| تجاوز بوابات Pages بجلسة مالك موقوف/محذوف | استعلام `catalogActor` يرفض وجود أي علامة تحكم غير نشطة مرتبطة بالحساب. يشمل `/api/catalog/*` و`/api/link/team`. | رفض جلسات الحساب الموقوف والمحذوف دون كتابة فريق أو بيانات. |
| إنشاء جلسة جديدة رغم التعطيل، أو تغيير كلمة المرور/تعطيل الموظف أثناء الدخول | إصدار الجلسة أصبح `INSERT ... SELECT` مشروطاً بوجود الحساب وحالته ونشاط الموظف ومطابقة salt/digest التي جرى التحقق منها. إذا لم يُدرج صف لا يصدر Cookie. | كلمة مرور صحيحة لا تنشئ جلسة للحساب المعطل؛ تغيير البصمة أو تعطيل الموظف بين التحقق والإصدار يمنع الجلسة. |
| حساب الكوزمتك يستخدم مسارات الصالون المباشرة لأن الدور الأساسي لكليهما owner | تحقق من هوية التطبيق المسجلة في قاعدة البيانات على مسارات المالك، دون الاعتماد على ترويسة عميل. استُبقيت مسارات me/logout وكشف الحساب وقبول الاتفاقية الخاصة بالكوزمتك. الحسابات القديمة بلا هوية تطبيق بقيت على سلوكها لتجنب كسرها. | خدمات الصالون والفريق مرفوضان للكوزمتك، بينما me وكشف حسابه يعملان. |
| معرض الصالون يعرض latest_revision المعلقة | استعمال published_revision بشرط approved وactive في مصدر الكتالوج؛ يبقى آخر إعلان معتمد مرئياً أثناء انتظار تعديل جديد. | نسخة الإنتاج الأصلية فشلت اختبار المعرض بعرض المراجعة المعلقة؛ النسخة المعدلة تعرض المعتمدة فقط. |
| وسيط إعلان غير معتمد قابل للوصول المباشر | فحص وسيط الإعلان يتبع المراجعة المنشورة المعتمدة، مع الحفاظ على المعاينة للمالك والإدارة وصلاحيات الموظف. | مجهول/مالك آخر/موظف مالية لا يقرأ الوسيط المعلق؛ المالك والإدارة يقرآن المعاينة؛ الوسيط المعتمد متاح للعامة. |
| الحساب المعطل يبقى في الكتالوج والفريق والوسائط العامة | تصفية حالة التحكم في استعلامات التسجيل المعتمد والكتالوج والفريق وتفويض الوسائط. | الصالون المحذوف يختفي من الكتالوج ولا يبقى وسيطه العام متاحاً بهذه الصفة. |
| بيانات الزبونة قبل قبول الحجز متاحة من API مباشرة رغم حجبها في Pages | تطبيق إخفاء الاسم والهاتف والملاحظات للحجز غير المؤكد/المكتمل في `workflowOwnerRoutes` نفسه. | هاتف الحجز المعلق محجوب؛ هاتف المؤكد يبقى متاحاً للصالون المالك. |
| سباق الحجز مع تعطيل الصالون أو إغلاق الموعد أو سحب اعتماد الخدمة أو حذف الزبونة | الإدراج نفسه يتحقق ذرياً من الحساب والتسجيل وحالة التحكم وهوية التطبيق، ووجود الزبونة المسجلة، وكتل الحجز بتوقيت بغداد، واستمرار المراجعات المنشورة المختارة. الإشعار والمكافأة يُدرجان فقط إذا وُجد الحجز الذي أُنشئ في المعاملة. | أربع حالات سباق محسومة قبل `batch`: لا حجز جديد ولا إشعار ولا مكافأة يتيمة. اختبار إضافي لمكافأة مستحقة فعلياً يمنع حجزها إذا سبق التعطيل. |
| خروج الزبونة من API القديم لا يلغي اشتراك الإشعارات | حذف الاشتراك المرتبط ببصمة الجلسة وحذف الجلسة في `D1.batch` واحدة. | الجلسة والاشتراك يُحذفان محلياً، والجلسة السابقة لا تقرأ me. |

لم تتغير عقود البيانات للعمليات الناجحة أو أسعار الحجوزات أو العمليات المالية أو ربط LEGACY_DB. النصوص البديلة لخصوصية الحجز هي السلوك الموجود أصلاً في بوابة Pages، ونُقل فرضه إلى المصدر.

## الاختبارات الفعلية

1. `node deployment/test-shared-api.mjs`: ناجح، باستخدام SQLite حقيقي في الذاكرة واستدعاء `default.fetch` للعامل الكامل، دون بوابة Pages. يغطي النشر والوسائط والصلاحيات والتعطيل والدخول وCSRF وترويسة صلاحية مزورة والحجوزات والتكرار والتداخل والخصوصية والخروج وحالات السباق المذكورة.
2. تشغيل المجموعة نفسها على المصدر الأصلي: فشل متوقع عند مقارنة معرض الإعلان؛ يعرض معرف المراجعة المعلقة بدلاً من المعتمدة. هذا دليل إعادة إنتاج، وليس فشل النسخة المعدلة.
3. `deployment/test-shared-api-runtime.mjs`: ناجح باستخدام Miniflare/workerd وD1 وR2 محلية مؤقتة. تحقق من SQL الحقيقي لبوابات الحجز، معاملة الحجز والإشعار، منع الموعد المغلق، التكرار الآمن، خصوصية الحجز المعلق، حجب الحساب المحذوف، تخزين/قراءة الوسائط، ومعاملة الخروج. كما تحققت استجابة مسارات HTML والسكربتات القائمة.
4. Miniflare المستخدم: `4.20260730.0` بتاريخ توافق محلي `2026-07-30`. تاريخ توافق الإنتاج الحالي `2026-10-26` لم يتغير. لذلك هذا تحقق runtime محلي، وليس اختباراً مطابقاً لكل إعدادات الإنتاج. أنواع Workers المسترجعة: `5.20261102.1`.
5. مجموعات `test-live` و`test-security-audit` و`test-account-deletion` و`test-notifications-audit`: جميعها بقيت ناجحة بعد إضافة المصدر.
6. `node --check workers/salonati-api/worker.mjs` و`git diff --check`: ناجحان.
7. `node deployment/verify-shared-api-assets.mjs`: **602,053 بايت من الأصول المضمّنة مطابقة تماماً** لبصمة نسخة الإنتاج؛ لم تُعدل الصفحات أو الألوان أو CSS أو سكربتات الواجهات. كذلك لم تتغير ملفات بناء Pages عن الجولة الأولى.

## حدود التسليم وما تبقى

- لم يُنشر Worker أو Pages ولم تُغير إعدادات أو أسرار أو تواريخ توافق، ولم تُنفذ عمليات حذف أو تعديل على قاعدة الإنتاج. لا يحتاج الإصلاح migration؛ الجداول المستخدمة موجودة بالفعل.
- لا يربط هذا الإصلاح الحذف النهائي المرحلي بواجهة حية، ولا يحدد سياسة احتفاظ بالسجل التشغيلي والمالي.
- خدمة `BOOKING_API` المستقلة وقاعدة البيانات القديمة لا تُعتمد آمنة أو مختبرة بالكامل بهذا الإصلاح. مسار تمرير QR القديم بقي كما هو؛ يحتاج اختباراً متكاملاً في بيئة مرحلية قبل اعتماد الجاهزية الشاملة.
- الحسابات القديمة غير المصنفة بهوية تطبيق تحتاج جرداً وترحيلاً متفقاً عليه قبل فرض منع شامل عليها؛ لم نحظرها اعتباطاً ولم ننقل ملكيتها.
- اختبارات الهاتف الفعلي والضغط والتنقل الداخلي والإشعارات على جهاز وقيود Google Maps ما زالت خارج الاختبارات المنجزة.
- يبقى طلب المراجعة مسودة. نشر API مستقل عن نشر Pages، ويحتاج مراجعة الفروق واعتماد النشر مع الاحتفاظ بالربط والأسرار الحالية وإمكانية الرجوع إلى النسخة السابقة. وجود المصدر في الفرع لا يعني تغير خدمة الإنتاج.
